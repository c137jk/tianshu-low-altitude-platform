1　引言

1.1　研究背景与意义

近年来，低空经济作为国家重点培育的新兴增长极，被多次写入政府工作报告，涵盖无人机物流配送、应急医疗救援、城市巡检、农林作业等多元业态。浙江省温州市作为低空经济先行示范区，已划定城市试飞空域并推进起降场网络建设。然而，当前低空运营仍面临空域资源供需失衡、飞行计划审批链条长、运营过程缺乏数字化监管手段、多角色协同不畅、飞行轨迹与违规事件难以留痕等突出问题。

本项目以温州城市低空物流为演示场景，设计并实现"天枢·低空智能运营管控平台"。平台将客户下单、商家调度、空管审批、机长执行、实时监控、结算归档全流程线上化，使分散的低空飞行活动转化为可监管、可计量、可追溯的数字资产。项目意义在于：一方面探索在课程周期内用轻量全栈技术栈实现复杂业务闭环的工程方法；另一方面通过 RBAC 多角色权限、双轨状态机、轨迹分区存储、敏感字段加密等设计，训练企业级系统在安全、隐私、可维护性等多重约束下的取舍能力。

1.2　研究目标与主要内容

1.2.1　研究目标

本项目最终目标是交付一套可运行的 B/S 架构低空运营管控系统，支撑"申请—审批—调度—监控—结算"全生命周期闭环：客户在门户完成下单与支付后，订单经商家接单、调度方案匹配、空管飞行计划审批、机长起飞执行，仿真器沿航线实时推进轨迹，前端在地图上刷新飞行器位置与告警，最终送达确认并结算。系统需满足九类角色权限严格隔离、订单与飞行计划双轨状态机一致、敏感个人信息加密存储、接口统一异常封装与操作日志留痕等企业级要求。

1.2.2　研究主要内容

系统按业务域划分为七大功能模块：

  • 账号与权限管理：账号密码登录、JWT 签发、企业/商家资质认证、RBAC 角色—权限树状分配、账号冻结解冻、操作日志审计。
  • 订单全流程管理：分步下单、服务空域校验与费用试算、Mock 在线支付、自动/手动接单、调度方案匹配与合规预检、订单实时跟踪、结算与评价投诉。
  • 低空资源管理：飞行器台账与健康度、起降场/换电站监控与预约、机长与运维人员资质及排班。
  • 空域合规运营：禁飞区/限飞区数据维护、飞行计划申报与审批、实时航迹比对与电子围栏告警、违规记录与分级处罚。
  • 数据统计与报表：运营大屏、多维度报表、Excel/CSV 导出。
  • 应急与客服：失联/闯区/低电量/恶劣天气分级告警、客服工单闭环、站内消息通知。
  • 系统配置：核心参数维护、商家审核、数据备份策略、全量操作日志查询。

3.2　系统架构设计

系统采用前后端分离的模块化单体架构，自上而下分为四层：

接入层（PC Web）：Vue 3 + TypeScript + Vite + Element Plus，含客户门户与管控台两套布局；高德 JS API 负责地图渲染与轨迹绘制，ECharts 负责运营大屏；Pinia 管理登录态，Vue-Router 按权限动态注册路由。

应用层（Flask）：按领域拆分为认证、订单、调度、空域、监控、资源、结算、统计、系统等 13 个蓝图；JWT 装饰器做接口鉴权，统一响应信封 {code, message, data}，全局异常处理器捕获 ApiError；APScheduler 驱动后台飞行仿真器与定时任务（资质到期、轨迹分区、券下架）。

数据层：MySQL 8.0 业务库；SQLAlchemy ORM 映射 35 张表；飞行轨迹按月 RANGE 分区。

外部适配层：UTM 空管、气象、支付、GCS 地面站全部以 Mock adapter 形式接入，将来替换真实接口只改动 adapter。

4　系统功能实现

4.1　登录与 RBAC 权限模块

登录页采用深蓝夜空视觉风格，提供账号、密码输入框与演示账号提示。用户提交后，后端在服务层校验用户名与 BCrypt 密码，账号不存在与密码错误返回同一句提示，避免账号枚举攻击；账号处于冻结或注销状态时拒绝登录。登录成功后，后端签发一对 JWT：访问令牌按设备类型区分有效期（PC 端 8 小时、移动端预留 2 小时），刷新令牌 7 天；同时返回当前用户信息与按角色聚合的权限菜单树。

前端拿到菜单树后动态注册路由：菜单型权限（perm_type=1）生成侧边栏，动作型权限平铺到 perms 数组；页面按钮通过 v-if="hasPerm('order:list')" 控制显隐。路由守卫在每次跳转时校验目标路由所需权限，无权限则跳 403；客户角色菜单为空，直接进入客户门户外壳。图 4-1 为登录界面。

图 4-1　用户登录页面

系统共内置 9 类角色、48 个权限点、8 个演示账号（密码统一为 Admin@123），覆盖平台管理员、商家、客户、机长、空管、运维、财务、维修等岗位。

4.2　订单全流程与调度状态机模块

客户在门户通过高德地图点选寄件点与收件点，选择物品类型、重量与时效后，后端根据起降场距离、空域费、加急系数实时试算费用并展示费用明细。提交订单后进入"待支付"，Mock 支付成功后变为"待接单"。商家在调度工作台看到待调度订单池，可自动匹配飞行器与机长或手动调整；方案保存后订单进入"待审批"，同时生成 1:1 绑定的飞行计划。

空管在审批台看到待审批队列，叠加禁飞区图层后通过或驳回；驳回时订单回退"待调度"允许商家调整重报。审批通过后下发给对应机长，机长在任务台确认起飞，订单进入"飞行中"。后台仿真器沿航线每秒插值推算坐标与电量并批量写入 flight_tracks，前端每 2 秒轮询刷新地图上的飞行器位置。到达收件点后机长确认送达，订单变为"已送达"，客户确认收货后归档为"已完成"。任何环节拒单、违规或应急终止都触发 Mock 退款并写入取消原因。整个过程由调度服务层统一驱动，业务端不能直接修改状态字段，只能调用动作接口，非法跳转被单元测试守护。

4.3　低空态势实时监控与数据大屏模块

监控中心在高德地图上叠加：当前飞行中的飞行器图标、计划航线折线、禁飞区/限飞区多边形、电子围栏边界。当仿真器注入偏航、闯禁飞区、低电量、失联等场景时，系统实时计算航迹与围栏的空间关系，触发对应级别的运行告警，告警在右上角滚动列表与顶部铃铛中同步提示；严重违规时弹窗强提醒。轨迹回放页面可选择历史飞行计划，按时间轴拖动回放飞行器历史位置。

5　核心代码

5.1　核心配置

全局配置全部从 .env 环境变量读取，代码中不写死密码与密钥。数据库连接池开启 pool_pre_ping 防止 MySQL 8 小时断连，连接 1 小时回收一次；JWT 按设备区分有效期；上传目录放在 instance/uploads 而非 static 下，避免上传件被同源直读；全站请求体限制 10MB。

5.2　实体类代码

所有业务实体继承 BaseModel，自动获得主键、创建时间、更新时间与逻辑删除四件套。用户实体中，敏感字段拆为"密文列 + HMAC 摘要列"两列：密文列用于展示时解密，摘要列用于等值检索（密文每次加密 nonce 不同，无法做 LIKE）；对外序列化统一走 to_login_dict()，保证密码哈希与密文永远不出现在接口出参中。

class TimestampMixin:
    created_at = db.Column(DateTime, nullable=False,
                          server_default=text("CURRENT_TIMESTAMP"))
    updated_at = db.Column(DateTime, nullable=False,
        server_default=text("CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP"))

class SoftDeleteMixin:
    deleted = db.Column(TINYINT, nullable=False, default=0, server_default="0")

class BaseModel(db.Model, TimestampMixin, SoftDeleteMixin):
    __abstract__ = True
    id = db.Column(BIGINT(unsigned=True), primary_key=True, autoincrement=True)


class User(BaseModel):
    __tablename__ = "users"
    username = db.Column(String(50), nullable=False, unique=True)
    password_hash = db.Column(String(100), nullable=False)
    user_type = db.Column(TINYINT, nullable=False)
    phone_cipher = db.Column(String(100), nullable=False)
    phone_digest = db.Column(CHAR(64), nullable=False, unique=True)
    email_cipher = db.Column(String(100))
    id_card_cipher = db.Column(String(100))
    status = db.Column(TINYINT, nullable=False, default=1)
    merchant_id = db.Column(BIGINT(unsigned=True), db.ForeignKey("merchants.id"))

    roles = db.relationship("Role", secondary=user_role, lazy="selectin", viewonly=True)

    def check_password(self, raw: str) -> bool:
        try:
            return bcrypt.checkpw(raw.encode(), self.password_hash.encode())
        except (ValueError, TypeError):
            return False

    def to_login_dict(self) -> dict:
        # 安全出参：不含任何密文与哈希
        return {"id": self.id, "username": self.username,
                "userType": self.user_type, "realName": self.real_name,
                "roles": self.role_codes, "perms": self.perm_codes}

5.4　服务层代码

视图层只负责收发参数，业务规则全部收敛在服务层。以登录服务为例：统一参数校验、账号状态判断、JWT 签发、菜单树组装都在 auth_service.login() 中完成；签发逻辑单独抽为 issue_tokens()，让登录与刷新令牌接口复用同一套 claims 与有效期口径。

def login(username, password, device_type, ip):
    if not username or not password:
        raise ApiError(BizCode.PARAM_ERROR, "请输入账号和密码")

    user = User.query.filter_by(username=username.strip(), deleted=0).first()
    # 账号不存在与密码错误给同一句提示，不泄露账号是否存在
    if user is None or not user.check_password(password):
        raise ApiError(BizCode.UNAUTHORIZED, "账号或密码错误", 401)

    if user.status == 2:
        raise ApiError(BizCode.FORBIDDEN,
                       f"账号已冻结：{user.frozen_reason or ''}", 403)
    if user.status == 3:
        raise ApiError(BizCode.FORBIDDEN, "账号已注销", 403)

    user.last_login_at = datetime.now()
    user.last_login_ip = ip
    db.session.commit()

    data = issue_tokens(user, device_type)
    data.update({"userInfo": user.to_login_dict(),
                 "menus": build_menu_tree(user)})
    return data


def issue_tokens(user, device_type):
    hours = 2 if device_type.upper() == "MOBILE" else 8
    claims = {"user_type": user.user_type,
              "roles": user.role_codes, "device": device_type.upper()}
    return {
        "token": create_access_token(identity=str(user.id),
                                     additional_claims=claims,
                                     expires_delta=timedelta(hours=hours)),
        "refreshToken": create_refresh_token(identity=str(user.id),
                                             additional_claims=claims,
                                             expires_delta=timedelta(days=7)),
    }

5.5　控制层代码

控制层以 Flask Blueprint 组织，每个蓝图对应一个业务域，统一挂在 /api 前缀下。需要鉴权的接口加 @jwt_required()，当前登录用户由 current_user() 装饰器注入；所有返回走 success(data, msg) 统一信封，异常通过抛出 ApiError 由全局处理器转换为标准错误 JSON。

bp = Blueprint("auth", __name__, url_prefix="/api/auth")

@bp.post("/login")
def login():
    body = request.get_json(silent=True) or {}
    data = auth_service.login(
        username=body.get("username", ""),
        password=body.get("password", ""),
        device_type=request.headers.get("Device-Type", "PC"),
        ip=request.remote_addr or "",
    )
    return success(data, "登录成功")

@bp.get("/me")
@jwt_required()
def me():
    user = current_user()
    return success({"userInfo": user.to_login_dict()})

@bp.get("/menus")
@jwt_required()
def menus():
    user = current_user()
    return success(auth_service.build_menu_tree(user))

@bp.post("/refresh")
@jwt_required(refresh=True)
def refresh():
    user = current_user()
    if user.status != 1:
        raise ApiError(BizCode.FORBIDDEN, "账号状态异常", 403)
    return success(auth_service.issue_tokens(user, "PC"), "登录态已续期")

7　结束语

7.1　总结

本项目从需求分析出发，完成了天枢低空运营管控平台的设计、开发与测试全流程。设计过程中遇到的主要问题与解决方法如下：

（1）双轨状态一致性问题。订单与飞行计划存在强绑定，若任由各端直接修改状态字段，极易出现"订单已起飞但计划仍待审批"这类不一致。解决方法是把所有状态变迁收敛到调度服务层的动作接口（接单、提交审批、审批通过、起飞、送达等），业务端不能直接写字段，并为每条合法路径与非法跳转编写单元测试守护。

（2）敏感信息存储与检索的矛盾。手机号加密后无法直接做等值查询和尾号检索。解决方法是"密文列 + HMAC 摘要列"双列设计：密文列用于解密展示，整号摘要列建唯一索引做查重与检索，尾号摘要列支持后 4 位模糊查找；出参统一走脱敏序列化方法。

（3）海量轨迹存储。飞行器每秒上报坐标，长期运行后轨迹表会急剧膨胀。解决方法是按时间 RANGE 分区 + 复合索引，并通过批量写入降低往返开销；回放时按时间范围裁剪分区，只扫描目标月份。

（4）多角色越权访问。初期曾出现"前端隐藏按钮但直接敲地址仍能打开页面"的问题。解决方法是路由由后端权限菜单动态注册，无权限的页面根本不进入路由表；接口层再做一次服务端鉴权与商家行级数据隔离，形成前端路由、接口装饰器、SQL 查询三层防护。

通过本项目，我完整经历了一个企业级系统从需求建模、数据库设计、前后端分离开发到测试的全过程，深入实践了 RBAC 权限模型、状态机设计、数据分区、加解密与审计日志等工程手段，也体会到在有限工期内对技术方案做务实取舍的重要性。
