天枢平台 — 数据库逻辑设计（设计稿 v0.4 · 滚动更新）
MySQL 8.0 / InnoDB / utf8mb4；已完成：全局约定、订单/计划/轨迹/审批、用户权限组（8 张）、资源组（5 张）、空域组（4 张）、交易支撑 P0 表；下一步汇总 E-R 图与可执行 DDL
一、全局建表约定（所有表统一遵守）
1. 表名、字段名一律小写+下划线，见名知意，避开 MySQL 关键字（如 order→orders、user→users）。
2. 每表标配四件套：id（BIGINT 自增主键）、created_at（创建时间）、updated_at（更新时间，ON UPDATE 自动刷新）、deleted（逻辑删除 0/1）。
3. 状态/类型字段用 TINYINT + 代码层字典，不存中文字符串（省空间、好索引、防脏数据）。
4. 金额一律 DECIMAL(10,2)，禁止 FLOAT/DOUBLE（浮点误差会算错钱）；坐标 DECIMAL，经度 10,6、纬度 9,6（6 位小数≈0.1 米），全库统一 GCJ-02。
5. 时间用 DATETIME 不用 VARCHAR；手机号等敏感信息入库加密/出参脱敏；文件只存 URL 路径不存文件本体。
6. 主外键体现约束；高频查询条件建组合索引并遵循最左前缀；历史/海量表（flight_track）按月分区。

五、六个设计门道（为什么这么建）
1. 双编号：自增 id 给数据库用（短、快），order_no 给人用（可读、不暴露平台单量、防遍历）。
2. 状态用数字不用中文：TINYINT 占 1 字节、索引快；中文释义放代码字典，界面再转中文。
3. 钱用 DECIMAL：FLOAT 会出现 0.1+0.2≠0.3 的误差，账目必须精确到分。
4. 费用在下单瞬间"冻结"成快照：事后平台调价不影响老订单，这就是需求报告允许的反范式。
5. 寄收地址冗余在订单里：而不是只存地址簿 id——客户后来改了地址簿，历史订单仍保留下单时的原样。
6. 订单表保持克制：航线/人机方案在 flight_plan，每次支付退款在 payment_transaction，月结账目在 settlement，订单只存结果，不背所有数据。

八、approval_record 审批流水表（P0 · 小表）
字段：id PK · plan_id（FK，索引）· approver_id 审批人 · result TINYINT（1通过 2驳回）· opinion VARCHAR(500) · created_at。
作用：驳回→修改→重提会产生多轮审批，本表保留完整审批历史，flight_plan 只存当前结果；计划书要求的"审批日志（审批人/时间/意见）"由它落地。
九、本批六个设计门道
1. 1:1 靠数据库强制：flight_plan.order_id 加 UNIQUE，一个订单永远只能有一个计划，不靠口头约定。
2. 一行走完一生：调度→申报→审批→执行四阶段分批填字段（方案 A 落地），不需要在多张方案表之间倒腾。
3. 热快照 + 冷流水分离：最新位置/电量冗余在 flight_plan.current_*（列表秒出），全量坐标在 flight_track（回放/取证），各查各的。
4. 航线用 JSON 字段：航点数量不固定，JSON 最灵活，前端高德拿过去直接画 Polyline，后端逐点做合规校验，不必为航点单建一张表。
5. 轨迹表为"写"而生：窄字段、批量插入、复合主键带分区键、按月分区；近 2 个月在线、更早整月归档（对应计划书历史数据归档要求）。
6. 审批留痕双保险：当前结果在 flight_plan 上方便列表展示，完整多轮历史在 approval_record 可审计。

十四、本组六个设计门道
1. 全角色一张 users 表：登录/JWT/冻结逻辑只写一套；user_type 管"你是谁"，RBAC 管"你能做什么"，两层不打架。
2. 手机号加密又能查的标准做法：AES 密文列负责解密展示（脱敏），另存 HMAC 摘要列负责精确查找和唯一约束——AES 带随机向量每次密文不同，不能直接拿密文查重。
3. RBAC 五表是行业通用解：权限树一套编码同时控制菜单、按钮和后端接口，前后端各拦一道。
4. role_scope 管数据范围：平台级看全量、商家级查询强制带 merchant_id、客户级只看本人——这就是计划书"数据层面按角色划分可见范围"的落地。
5. 资质表多态复用：subject_type+subject_id 一张表同时服务商家和机长，到期预警只靠一条 expire_at 索引扫描。
6. 密码只存 BCrypt 哈希：数据库泄露也无法还原明文；连输错 5 次锁定的逻辑放 Redis 计数，不污染用户表。

十九、本组设计门道
1. 资源台账与实时状态分离：aircraft/vertiport 存静态台账 + 最新状态快照，高频心跳在 Redis，落库节奏由定时任务控制，避免每秒刷库。
2. 健康度是算出来的不是拍的：维保记录、故障次数、累计飞行时长共同计算 health_score，前端按红黄绿渲染。
3. 冲突靠唯一索引兜底：排班重复、场站同时段超额，业务层先校验、数据库唯一约束再兜底，双保险。
4. 空域几何与业务数据分离：airspace 只描述"哪块空域、什么规则"，是否违规是实时计算结果并落到 violation_record + 轨迹点打标，不回写污染空域表。
5. 资金两张表分工：orders/settlement 记"该收/该结多少"（结果），payment_transaction 记"每次支付退款动作"（流水），对账时以流水核对结果。
