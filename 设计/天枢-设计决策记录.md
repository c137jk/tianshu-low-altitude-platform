补充决策（设计件未细化、实施时补定，代码注释为权威）：

* D-29 定价公式：基础运费 = 航线距离(km)×3.5 + 重量(kg)×1.2（取自商家 pricing_json：basePerKm=3.5、perKg=1.2）；航线每穿越 1 个限飞区收空域服务费 10 元；穿越禁飞区/临时管制区直接拒单（40900）；加急费 = 基础运费×50%；演示巡航速度 12 m/s。

## 六、W3 调度审批域实施记录（2026-09-21 完成并实测通过）

**范围**：后端 D3 调度/审批/执行域（48 项自测断言全过）；前端批3 七个页面（M-21/22/31/32/33/34/35）；L2 造数补齐在途 7 单 + 5 计划；浏览器全链路实测（商家出方案→空管批量通过/驳回必填→商家下发→机长起飞/降落→驳回重报闭环）。

补充决策：

* D-34 资源占用口径：只有「执行中(status=3)」或「已批准且已下发(status=2 且 assigned_at 非空)」的计划才锁定机长/飞机；待申报、待审批、已批准未下发均不占资源。飞机状态仅在起飞时变 2、降落归 1。
* D-35 新增权限点 33 号 `dispatch:execute`（起飞/降落确认），仅授予机长角色；调度员/商家管理员有 plan/submit/assign 无 execute，空管有 approval:handle 无 execute；平台管理员自动全权限。演示机长账号 pilot 陈机长、pilot02 林机长（现网库按 username 幂等创建，id 不写死）。
* D-36 外部系统全部走 Mock 适配器：气象（经纬度网格+小时确定性伪随机，约 90% 适飞，返回风速/风向/能见度/温度/预警等级）、UTM 空管申报（返回 UTM 申报号）、GCS 地面站（下发返回 GCS 指令号）；适配器接口即未来真实对接的防腐层。
* D-37 造数短驳策略：在途演示单（含调度台待调度池）只从瓯江口核心区 5 个相邻点（1.5~5km，全在可飞示范区）配对，保证一键推荐必然通过航程/电量校验；历史长航程单仍保留在基础订单池中（其中 blocked 单用于演示系统拦截能力）。调度台默认自动选中第一单「可推荐」订单，blocked 单保留在池中可点选查看原因。
* D-38 地图视野口径：调度工作台框定「空域+航线」全局态势；审批台/计划详情/机长任务台只框定航线与起降点（fit='route'），空域多边形照常绘制但不主导视野。setFitView 对 Text/Polygon 在地图 complete 前可能失效（会缩到全国），统一改为手动计算 AMap.Bounds + complete 事件 + 300ms 延时兜底。

经验教训：

* 自测脚本中 HTTP 请求不能包在长驻 `app.app_context()` 里——Flask 测试请求会复用外层 g，current_user 缓存成首个登录用户导致串号；HTTP 调用放模块级、DB 操作切短上下文块。
* 禁飞场景不能走 estimate 造数（D2 入口即 409），测试中直接 ORM 造脏单验证 recommend blocked 与建方案 409。
* 前端表格/三栏页的 grid 列必须 `min-width:0`，否则 Element 表格/描述列表的 min-content 会把右栏挤到 85px。
* 机长任务台起飞/降落后必须主动切换 Tab（起飞→执行中、降落→全部）并按最新状态重选当前卡片，否则列表过滤状态与右侧详情不一致。
* 计划列表「下发机长」按钮在 assigned_at 非空后必须消失（已下发的任务不能重复下发）。

实测结论：merchant 接单→调度台一键推荐（飞机/机长/起降场自动回填、航程航时电量、气象、人机校验）→保存方案→提交申报（UTM 号）→admin 批量通过（2 张）/单条驳回（原因必填校验）→merchant 下发（GCS 号）→pilot 起飞前检查弹窗→执行中实时面板/地图航线视野→确认降落送达（计划已完成、飞机归位）→驳回单详情显示原因与时间线、「重新出方案」跳回调度台并自动选中该单，全部通过；type-check 零错误、build 通过（chunk>500kB 为 W6 已知技术债）。实时位置移动与秒级推送留给 W4 飞行仿真器 + WebSocket（当前 5s 轮询占位）。

## 七、地图坐标纠偏与航线语义澄清（2026-09-22 完成并实测通过）

**起因**：演示中发现订单地名（如「温州湾未来科技城」「灵昆街道」）与地图标记实际位置相差数公里；同一条航线同时出现「发货/签收/起飞/降落」多个标记，短途单看起来像「中途还要降落一次」。

排查结论与决策：

* D-39 全部演示地理点以高德地理编码为准：初版 12 个 PLACES 与 2 个场站坐标为手估，偏差 3~10km（旧 VP1 逆地理落在乐清市）。已用高德 Web 服务 geocode 逐个核准（GCJ-02）：VP1 瓯江口综合示范站（120.9295,27.9555，灵昆岛）、VP2 龙湾城市起降场（120.815,27.945）；可飞示范区多边形改为 120.885~120.975 / 27.915~27.975（与机场禁飞框东界 120.880 留 500m 缝）；5 个短驳核心点（管委会/新月公园/未来科技城/灵昆街道/瓯江口医院）脚本验证全部落在可飞区内、航线零禁飞穿越。DDL、一次性幂等迁移脚本 migrate_geo_20260922.py、造数 PLACES 三处同源修正并 --force 重建。
* D-40 航线四段语义与展示口径：业务航线固定为「起飞场→寄件点（取货）→收件点（投递）→降落场（调机返场）」。寄/收是客户货物的门址，起/降是固定 vertiport 枢纽（净空、充电、装货、监管）。短途门到门演示单起、降场为同一个 VP1，不存在「中途降落」；之前的视觉误读来自起/降两个标记重叠 + 返场航段与载货航段同一样式。前端统一改为：载货航段金色实线带方向箭头，收件点→降落场的返场航段浅金虚线（opacity .5、无箭头）；起/降坐标相同时合并为单个藏青「场」标记（悬停提示「（起飞/返场）」）。调度台图例增加「载货航线/调机返场」。
* D-41 计划 VO 直接带场站经纬度（takeoffVertiportLng/Lat、landingVertiportLng/Lat）：机长角色无 dispatch:plan 权限、调 /dispatch/resources 会 403，此前机长任务台/计划详情缺起/降标记；改为详情接口直接给坐标，资源表仅作回退。

* **更正 W3 那条「DB 操作切短上下文块」**：Flask 3 的 `RequestContext.push()` 发现栈顶已是同一个 app 的上下文就直接复用（`flask/ctx.py`），所以 `test_client` 发出的请求和用例本身**共用一条 session、共用一个 `g`**。在用例里再套 `with app.app_context()` 改数据，会多出一条 session：那边提交完，这边身份表里的对象还是旧的 status=1，请求读到脏快照——冻结账号照样能续期这种"该拦的没拦住"会以**假通过**形式出现。改数据要在当前上下文里直接改并 commit；`g` 不随请求重置，也正是 `current_user()` 的缓存键必须带 JWT sub 的原因。

* 生产加固要顺藤摸到同类：一个 `int(脏值)` 冒 500，背后是每个从请求取数字的地方都会；补一个 `_int_or_400` 收口，比逐处 try/except 更不会再漏。

经验教训：

* **"打不开"几乎都是落点写死**：一个 `code→path` 常量表不看权限，就会同时造出"点了没反应"（弹回首页）和"404"（命中兜底）两种现象，而它们看起来像两个不同的 bug。落点、侧边栏、路由注册必须同源。
* 默认值也是设计：默认页签、默认倍速、按钮的 `disabled` 条件都会决定一个功能是"能用"还是"看不见"。60× 与「待申报」都不是错值，只是错在**对所有人都是同一个值**。
* 状态机正确 ≠ 用户看得见：订单状态一路推进，但从"待调度池"消失之后就再无踪迹——流程可观测性和流程正确性是两件事。

补充决策：

* D-73 **对账必须是"账单 vs 支付流水"的真比对，不是状态位搬运**。原 `reconcile` 把 `status=1` 统统写成 2，
  一次流水都不查——这在演示里是"走完了流程"，在答辩里是一问就穿。现在逐单取流水净额
  （`direction=1 & status=2` 之和 − `direction=2 & status=4` 之和）与账单核，平→2，不平→4 并回差异清单。
  待支付/失败/退款中的流水一律不算到账，这正是差异的来源而不是噪声。
* D-74 **一列一义**：`settlement.pay_amount` 定为"向客户收取的钱"（= 订单实付 = 应等于流水净额），
  商家实收降级成派生列 `merchantIncome = pay_amount − platform_fee`。种子脚本原本按"扣完抽成的实收"记账，
  与 `confirm_receipt()` 的全额写法在同一个库里并存；这条不先统一，对账一上线就是"12 笔种子账单全差异"，
  差额恰好等于平台抽成——**功能是对的，数据是假的，比功能缺失更难查**。营收口径同时与监管报告的
  `SUM(orders.pay_amount)` 对齐。
* D-75 **对账要先上锁再核**：命中的账单先集体置 `status=3 对账中` 并 commit，再逐单判定写 2/4。
  两个财务同时点按钮时，第二个抓不到 3 以外的单，不会重复处理；`RECON_FROM=(1,3,4)` 留两个口子——
  3 是"上一次崩在中途"的自愈路径，4 让财务补完流水后能重核同一笔。已结算(2)不进，避免一键把整本账重跑。
* D-76 **流水的商家归属跟订单走**：`payment_transaction` 没有 `merchant_id`，收窄必须
  `JOIN orders` 按 `orders.merchant_id` 过滤。与 D-63（`maintenance_record` 靠 `aircraft.merchant_id`）同一条规律：
  数据范围要看"归属字段实际在哪张表"，不能看表名想当然。`ids` 显式勾选同样过范围过滤，
  传别家账单 id 只会命中 0 条（409），不会把别人的账核掉。
* D-77 **开票拆成两个动作两种权限**：申请（0→1，`settlement:list`，商家/财务都能提）与

  并给其中金额最大的一笔补一条售后部分退款流水作差异样本。只新增流水，不改订单与账单金额。
* D-79 结算用例不依赖演示库账号名（`caiwu` 是演示库后建的，测试库种子账号只有 5 个），

补充决策：

* D-80 **手机号检索走摘要列，不走密文**。`orders.sender_phone` 是 AES-256-GCM 密文，每次加密 nonce 随机，
  同两个号两次密文都不一样——`LIKE '%13900000001%'` 永远 0 命中，而界面上的搜索框一直写着"支持手机号"。
  补 `*_phone_digest`（整号 HMAC）+ `*_phone_tail`（后 4 位 HMAC）四列做等值检索。
  **不存明文尾号**：需求 10.4 承诺 PII 密文落库，存一列明文 `1391` 等于自己开旁路；客户记住的本来就是尾号，摘要能等值匹配就够。
* D-81 **HMAC 密钥与 AES 派生密钥分家，且必须等于 DDL 种子那把**。修检索时顺带查出：代码用
  `HMAC(sha256(secret), phone)`，而 DDL 7.5 的种子摘要按 `HMAC(原始密钥, phone)` 生成，两套值永远对不上——
  运行时写入的 13 行 `users.phone_digest` 全部检索不到，`system.py` 的手机号查重形同虚设（用同一个号能注册第二个账号）。
  现在 `_HMAC_KEY = _SECRET`（原始字节），AES 仍用 sha256 派生，顺带满足"同一份密钥材料不复用于 AES 和 HMAC"。
  回填脚本第一步是 `_key_selfcheck()`：拿 `users.admin` 的已知手机号反查摘要，对不上就大声报警——
  **配置里躺着 `PHONE_HMAC_KEY`、代码读的是 `TIANSHU_PHONE_KEY`，这种"两个名字"的坑必须有个自证机制**，否则下次是静默失效。
* D-82 **导出单独设 `order:export` 权限点，不蹭 `order:list`**：导出是"把姓名+电话+地址成批搬出系统"，
  和在工作台翻一页不是一个量级。导出口径 = 列表口径（同一个 `_filters()`、同一套 `_scope_query`），
  服务端上限 5000 行，超出时 `X-Export-Truncated` 提示收窄条件；自定义响应头必须显式
  `Access-Control-Expose-Headers`，否则浏览器读不到。
* D-83 **文件流下载绕开信封拦截器**：`utils/request.ts` 的响应拦截器把 `{code,message,data}` 拆成 `data`，
  Blob 响应没有 `code` 字段会被当成业务错误 reject。新增 `utils/download.ts` 用裸 axios（与 `requestNewToken` 同一先例），
  自己带 `TOKEN_KEY`、`responseType:'blob'`，失败时把"伪装成 CSV 的 JSON 错误信封"解出来再弹。
* D-84 **服务空域要成为闸门就得有几何；几何按"库里实际在跑的数据"画，不按种子画**。
  旧值 `JSON_ARRAY('瓯江口新区','龙湾区')` 只有名字，订单表没有区域字段，判"在不在范围内"要逆地理编码（演示环境没有），
  所以 p12 给商家补了 Polygon。**第一版按 DDL 7.4 的两座种子场站画了 120.76~120.99 的框，
  把演示库里实际在跑的温州南站(120.669,28.012)、温州商学院(120.700,27.913) 整个漏在框外**——
  演示库是边演示边长出来的，DDL 只是初始种子，照那个框下单会 100% 被"超出服务空域"拒掉。
  现在框取 120.60~121.00 / 27.88~28.05（罩住两座种子场站 + 全部演示场站 + 62 个历史订单端点聚簇），
  迁移里额外补一条只认"上一版那个窄框首点"的纠正语句（人工配过的不覆盖，重跑幂等）。
  另两条口径同时钉住：**几何缺失 ⇒ 不拦**（商家配漏了不能把下单链路堵死）；**服务区与禁飞区是两道独立闸门**
  （龙湾净空禁飞区有意落在服务区内部，穿过去照样拒）。
* D-85 **批量导入复用单个下单的同一条校验链**（禁运品 → 坐标 → 服务空域 → 重量 → 距离 → 禁飞区），
  逐行 `try/except + rollback`，失败行不带走整批；`dryRun=1` 只校验不落库。
  模板**不带示例行**（示例行会被连文件一起传上来，然后真的下成一单），格式提示全写进表头括号；
  解析器接受中/英/带星/带提示四种表头形态，`decode()` 依次试 utf-8-sig → gbk（WPS 另存的 CSV 是 GBK）。
* D-86 **强制终止是 0~4 段唯一出口，三条取消路径共用 `_mock_refund()`**。客户自助取消只能到「待接单」，
  订单进了调度/审批就没有整单作废的口子；新增 `order:force_cancel`（平台+商家，服务层再按 merchant_scope 收口），
  顺带作废关联的在途调度方案（`flight_plan.status=6`）并通知客户。
  退款写流水的口径必须三处一致（取消/拒单/强制终止），否则 B1 的对账净额会因路径不同而差异。
  「飞行中」及之后不在本口子内——那是应急处置，不是取消订单。
* D-87 **筛选下拉的候选值从订单表 distinct，不查 `merchants` 表**：那是资源模块的数据范围（要 `resource:merchant` 权限），
  订单页只需要"我看得见的那些单里出现过哪些商家/品类"，既不开新权限，也不会把人导到搜出空结果的选项上。
* D-88 **Vue 的 Boolean prop 收到 `''` 会变成 `true`**：`:disabled="!picked || busy"`（`busy` 是字符串状态量）
  在空闲时求值为 `''`，el-button 把它按 Boolean prop 转成 `true`，于是"选了文件按钮还是灰的"。
  布尔属性一律给真布尔（`!!busy`）。这类问题 `vue-tsc` 查不出来，只有真点一遍才发现。

* **"placeholder 写着支持手机号"和"能搜手机号"是两件事**：密文不可 LIKE 是加密方案本身的性质，
  不是漏了个 `WHERE`。可检索的 PII 必须显式设计摘要列 + 回填 + 用例，缺一环就是恒 0 结果的静默故障。

细节与证据见《差距分析》§15。

补充决策：

* D-89 **回放游标按真实 `track_time` 推进，不按帧号步进**。仿真器落帧用的是
  `track_time = 起飞时刻 + 仿真已过时间`，倍速 ×60 时两帧之间可能隔 60 秒仿真时间；注入失联时不落帧、
  帧数上限截断时也会留空洞（实测库里 3~124 帧、跨度 60s~4h）。按帧号播会把"断了 3 分钟"演成"停了 3 帧"，
  正是要避免的粉饰。配套口径：**位置可插值**（相邻两帧按时间比例取点，飞机不跳格），
  **遥测读数不插值**（高度/速度/电量只显示最近一帧真值——插出来的电量就是编数据）。
* D-90 **选中计划时按轨迹总时长自动挑倍速**，档位 `[1,2,5,10,20,50,100]` 里取"约 1 分钟播完"的那一档。
  给固定 1× 等于让一条 4 小时的轨迹永远播不完，给固定 100× 等于让一条 60 秒的轨迹一闪而过；
  倍速仍可手改，自动值只是初值。
* D-91 **违规 tag 的中文在出参侧翻译，前端不维护第二份映射**。`flight_track.violation_type` 存的是
  英文 tag（`no_fly_intrusion` 等），中文在 `app/models/compliance.py` 的 `VIOLATION_TYPE/VIOLATION_TAG` 里；
  回放接口用 `TAG_NAME = {v: VIOLATION_TYPE[k] for k, v in VIOLATION_TAG.items()}` 反查输出 `violationName`。
  再抄一份中文到前端，就是下一次改枚举时的漏网之鱼。
* D-92 **`GET /monitor/tracks` 不筛 `status`**：在飞（status=3）的计划同样逐帧落库，回放页要能边飞边看。
  这个决定反直觉（"回放"听起来是历史功能），所以写进 docstring，免得下次被"顺手加个 status=4"改回去。
* D-93 **设备在线不建 `device` 台账表，状态一律推导，只有"人工判断"才落库**。平台里的设备就是
  `aircraft`（机载终端）和 `vertiport`（地面设备），再造一张表只会多出一份没人维护的副本；
  "在线/离线"能从数据推出来（心跳新不新、有没有在飞计划），存下来必然两张皮。
  唯一存不下的是运维口头那句"这台图传丢了、先按失联处理"，所以只建 `device_lost_mark
  (device_type, device_id, reason, marked_by, marked_at)`，`uk_lost_device` + `ON DUPLICATE KEY UPDATE`
  保证一台设备一条，解除标记 = 删行、状态自动回到按心跳判定。
* D-94 **心跳取"最近一次真实写入时间"，不做"看起来全在线"**。机载终端取
  `max(aircraft.updated_at, 在飞计划的 last_report_at)`，阈值走 `sys_config.device_heartbeat_timeout_sec`（默认 60s）；
  三态判据里最关键的一条是**有在飞计划但心跳断了 → 失联**（这才是要人处置的），停场无遥测 → 离线。
  地面设备根本没有遥测链路，状态取场站运营状态，出参打 `heartbeatKind:"record"`，
  界面上那一列写成"资料更新"而不是"心跳"——答辩时这一条一定会被问。
* D-95 **"解除失联"按钮只在存在人工标记时出现**。系统按心跳判出的失联，删标记解不掉，
  给一个点了没用的按钮比不给按钮更糟。同理电量红色分档由接口下发 `batteryThreshold`
  （读 `battery_return_threshold`，与后端返航判定同源），前端不再自己猜一个 20。
* D-96 **`monitor:device` 是新权限点，且必须补 `role_permission`**：DDL 里平台管理员是
  `SELECT id FROM permission` 一次性铺满的，新增点不补授权连 admin 都看不见菜单。
  授 1 平台管理员 / 2 空管 / 3 运维 / 8 商家运维；机长、客户实测 40300。
* D-97 **监管报告页只做"把已有 17 个字段铺出来"，不新增统计口径**。`/aux/report` 早就返回
  15 个基础统计 + `completionRate` / `violationRate`，缺的只是页面；明细（违规台账、处罚与
  《违规处理通知书》、应急时间线）留在「违规处置」「应急处置」tab，那一侧已有 CSV 导出。
  同一件事在两个页面各算一遍，是"监管报送数字对不上"的标准来源。
* D-98 **`el-progress` 带 `:status` 会把百分比文字换成状态图标**——于是"电量"列只剩图标、读不到数。
  这个写法散在三处（新页 `Devices.vue`、既有的 `resource/Aircraft.vue`、`resource/Vertiports.vue` 使用统计），
  统一改 `:show-text="false"` + 旁边单独写读数。`vue-tsc` 和构建都查不出来，只有真开一遍页面才发现。
* D-99 **卡片栅格按内容最坏情况定列数**：`Report.vue` 四组卡片用 `:span="6"` 时，中文标签在窄视口里
  逐字换行（"已¥2,支付付营收"）。改 `:span="12" :lg="6"` + `.line span/b { white-space: nowrap }`，
  实测 671px 视口下卡片 199px 宽仍 0 溢出。CJK 排版宁可撑开列宽也不能按汉字折行。

经验教训：

* **"能选计划画条线"和"能回放"是两个功能**：前者是接口 + 一张静态图，后者要有时间轴、倍速、
  违规点跳转和遥测曲线。差距分析里 M-62 标的"约 20%"是准的，做的时候才发现难点全在
  "帧间隔本来就不规则"这一条性质上（D-89）。
* 推导出来的状态比存出来的状态诚实，但**必须在界面上说清它是推导的**（D-94 的 `heartbeatKind`、
  "资料更新"字样、15.2 的说明段）。否则运维会以为地面设备真的有心跳，出了事回头怪系统漏报。
* 两个 pytest 进程同时跑会共用 `tianshu_test`，表现为一批 `AttributeError` / SQL 失败的**假红**。
  本批就差点把这批假失败当成回归去"修代码"。跑第二遍前必须确认第一遍已结束。

实测结论：`pytest` 200 用例全绿（新增 11 例：回放列表含状态与帧数/跨度、详情时间线与 `violationName`、
未知 planId 404、匿名 401 与 customer 40300 门禁、心跳新→在线、在飞且心跳断→失联、
停场且心跳旧→离线、地面设备取运营状态且 `heartbeatKind=record`、标记-重复标记只留一条-解除、
入参 40000/40400、pilot 40300 vs merchant_maintainer 0）；
`vue-tsc --noEmit` 0 错误；`vite build` 通过；`export_perm_matrix.py` 端点 130（+3）/ 权限点 44（+1）/ 角色 9 / 未归类 0。
p13 迁移落演示库、重跑幂等；`device_lost_mark` 收尾 0 行（标记-解除往返是现场做的，没留残留）。
浏览器实测：回放页 13 个有帧计划、7 个违规刻度、100× 播放时刻 15:40:41→15:40:46 正常推进、
暂停图标切换、违规跳转回绕（超时飞行 ↔ 偏航 ↔ 闯禁飞区）、刻度点击 seek、两张曲线 canvas + 高德分色轨迹；

`sql/migrations/20260929_p14_station_reservation.sql`、`app/blueprints/aux.py`、
`app/services/{geo,dispatch_service,compliance_monitor}.py`、`app/blueprints/airspace.py`；
测试新增 4 模块 62 例（`test_resource_aircraft` 11 / `test_station_reservation` 19 /
`test_altitude_admission` 11 / `test_airspace_ledger` 21）+ `conftest.py` 空域清场；

`airspace/{AirspaceList,AirspaceMap,Geofence}.vue`、`api/{resource,dispatch,airspace}.ts`。
细节与证据见《差距分析》§16。

补充决策：

* D-100 **详情接口比列表更容易漏数据范围**。`GET /resource/aircraft/<id>` 用
  `perm_any_required("resource:aircraft","dispatch:plan","monitor:realtime")` 放宽读权限——调度台和监控台
  点开机号要能回答"这台机为什么不在派单池里"，只给资源权限它们跳进来就是 403。
  但放宽权限点不等于放宽数据范围：`scope.merchant_filter` 必须在详情里再判一次（非本商家 403），
  否则详情就成了绕过列表收窄的那条通道。
* D-101 **履历时长分"实际"与"申报"两种真值**，出参额外带 `actual: bool`：落过地才给
  `actual_landing - actual_takeoff`，未落地只能给 `est_duration_sec`。两者混进同一个数字就是编数据，
  前端据此把非实际的标成"申报"。
* D-102 **MySQL 的 `SUM(...)` 是 DECIMAL，不经转换会序列化成 JSON 字符串 `"4"`**，
  前端拿去做数值比较静默出错。统计出参一律显式 `int()`。
* D-103 **维保接地只认"定期维保/故障维修"两类，巡检不接地**。原实现三种类型一律把机器置 4，
  等于逼运维多点一次"完结"才能继续用——巡检本来就是停场时顺带做的一项检查。
  接地还必须 `WHERE status IN (1,3)`：正在执行中的机器不该被台账里勾的一条记录拉去维保。
* D-104 **完结时先查"还有没有在办记录"才放回派单池**：一台机可能同时挂两条报修，
  只完结一条就恢复"闲置"等于绕过接地。同一处顺带把 `next_maintain_at` 按 `maintain_cycle_days` 推后，
  否则巡检台账永远显示过期。
* D-105 **机位"占位"口径包含待审（`status IN (1,2)`），且起降与充换电是两个池子**
  （泊位看 `capacity`，换电/充电共用 `charger_total`）。只算"已通过"的话两个商家各自排队申请都能通过、
  一起放下来就超容；审核放行时再用同一个 `_check_slot()` 核一次（`exclude_id` 排除这张待审单自己）——
  **申请与审核两处必须共用一个函数**，各写一份判据迟早长歪，而长歪的表现就是超容放行。
* D-106 **预约的 `merchant_id` 只信登录态**，平台侧代商家申请必须显式给 `merchantId`；
  随手填的 `aircraftId` 要校验归属（列表按机号展示，抄别家机号等于把对方台账抄进自己记录）。
  审核权单拆一个点 `resource:reservation:audit`（id=46，只授平台管理员/运维），
  商家侧永远不能自己放行；列表读口放宽到 `reservation | vertiport | dispatch:plan`，因为调度台要看机位占用。
* D-107 **"已通过"必须有终点**：时段已开始的通过单不给直接取消（要先完成或改期）、
  时段未结束不给提前回执完成。否则占位永远释放不掉，机位被幽灵预约吃掉。
* D-108 **高度准入三处共用一个纯函数 `geo.binding_ceiling()`**（申报前 `create_plan`、提交前 `submit_plan`、
  飞行中 `compliance_monitor`）。判据是"被超过的那些上限里最低的那个"：旧实现飞行中取"第一个命中"配
  "最大超限值"，两个空域套叠时会把责任推到宽松的那个上（写出"超过甲空域上限 60m"而 60 其实是乙的上限）。
  `None` 表示该空域不限高，参与候选但不兜底；兜底是全局 `altitude_limit_max_m`（配置驱动，用例会改参数
  并清缓存来证明不是写死的 120）。
* D-109 **限飞区不是禁飞区**：穿过去本身合法，只有申报高度超上限才拦。所以用例必须同时钉
  "超上限拦下"和"改成合法高度放行"，否则很容易写歪成"穿了限飞区就拒"。
* D-110 **提交申报时按存量航线重判一次**：方案起草后空域可能被重画或限高被收紧，
  不重判等于让"待申报"里躺着的老方案带着已经失效的合规结论飞出去。
* D-111 **推荐高度由服务端压到区限以下**并写进 `warnings`，`route-preview` 下发 `altitudeMax` 与
  `altitudeLimitFrom`，前端不做第二套几何判定。否则操作员一进来看到一个"合法"的 100m、点保存才被闸口拒掉，
  等于把服务端的判断推给了人。
* D-112 **空域"回到待审核"按值有没有真变判，不按字段有没有出现判**。编辑表单每次都会把 `geometry`
  原样回填再提交，按 key 存在判改动 → **只改一个名字也把已生效的空域打成待审核、直接退出合规判定**，
  表现和误撤区一模一样。几何、类型、管制起止四项各自与旧值比较后才置 `touched_geometry`。
* D-113 **下架（删除）需要 `airspace:audit` 而不是 `draw`**：删除等于把判定依据整体撤掉，是审核级动作。
  另两条闸门：`source=1`（空管同步下发）不许删、只许停用——删了下一次同步还会原样下发回来，
  给了删除按钮就是骗人；范围内仍有在飞任务时 409 并把计划号点名出来。下架走逻辑删除并留一条站内信。
* D-114 **前端编辑多边形必须读回真实环**：`openEdit()` 原来取首尾两点拼外接矩形，
  非矩形空域被编辑一次就无声变形（等于悄悄改了判定范围）。改为 `ring.slice(0, -1)` 逐顶点续画、右键回退。
* D-115 **用例现画的空域必须外清**（`conftest.py` 补 `DELETE FROM airspace WHERE id NOT IN (1,2,3)`）：
  它会一直留在 `all=1` 台账里并被 `active_airspaces` 捞去参与判定，让后面任何一条飞行链路用例
  莫名多出一个"闯区"——这类外溢表现为别人家的用例变红，最难查。

经验教训：

* 本批四条 P1，三条的难点都不在页面而在**口径**：机位怎么算占用、限高取哪一个、什么时候才算改了空域。
  接口能通只是一半，"和判定同源的那一个口径"才是交付——D-105/D-108/D-112 三条都是这一类。
* 三个看起来像前端的缺陷，根因全在服务端与数据层：`SUM` 的 DECIMAL 类型（D-102）、

  现在申报前、提交前、飞行中三处同一结论，机长拿到的是"能不能飞"，不是"飞了以后为什么违规"。

## 十五、B5 营销与准入批次：优惠券全链路、商家入驻审核、消息通知写入 hook（2026-09-29 完成，后端 302 例与接口实测通过，页面人工实测待补）

* D-116 **券链路只补一张关系表 `user_coupon`，不存券面规则快照**：coupon 表与后台增删改早就通了，
  缺的是"谁领了哪张、抵扣落在哪一单"（差距分析 §7.1）。规则快照会让运营改一次门槛就造出
  一批各自漂移的旧券；真正必须冻结的是"这一单减了多少钱"，那个数字属于 `orders.discount_amount`——
  **券是规则，订单是结果**。
* D-117 **能推导的状态一律不落库**：券包里的 `4 已过期 / 5 券已停用` 由 `coupon.end_at` 与 `coupon.status`
  现判（`coupon_service.expired_of()/_ser()`），库里只有 1 未使用 / 2 已核销。存一份过期态就等于
  允许多一个需要定时任务维护的真相，运营把券续期之后那张"表里已过期"的券会谁都不认。
  定时归档留给 B6，但读时推导已经保证页面不会显示错的态。
* D-118 **限量与限领都在 SQL 层兜住，不靠先查后写**：领券是
  `UPDATE coupon SET got_count = got_count + 1 WHERE ... AND got_count < total_count` 的条件自增
  （`.rowcount==0` 就是刚被领完），每人一张靠唯一键 `uk_user_coupon`，插入撞唯一键时把刚抢到的名额
  一起回滚——否则一次失败的领取会白白吃掉一个名额。核销同理：只有 `status=1` 才写得进，
  同一张券提交两单时只有一单占得住。
* D-119 **抵扣只算一次、两处共用**：`/orders/estimate` 与 `create_order` 都走 `coupon_service.discount_for()`。
  页面价与扣款价分叉是本项目最难解释的一类缺陷，把口径收成一个函数比写两遍再对账便宜。
  核销 `settle()` 挂在 `create_order` 的同一个事务里，抢不到券就整笔回滚。
* D-120 **`couponId` 传券包 id（`user_coupon.id`）而不是券模板 id**：同一张模板券人人都有，
  只有券包 id 才分得清是谁的那一张。所以下单页选券框的数据源是"我的券包"，不是领券中心；
  门槛不够的券前端直接置灰（同服务端口径），但服务端仍是最终裁决。
* D-121 **门槛按原价判而不是折后价**：否则一张券可以反复叠加把价格一路压低。
  校验顺序固定为 归属 → 状态 → 有效期 → 门槛，归属放最前，别人的券连券号都不该泄露（用例钉成 404）。
* D-122 **退券三条作废路径共用一个函数**：取消、商家拒单、平台强制终止都走
  `order_service._return_coupon()` → `coupon_service.release_for_order()`，确认收货不退（券已随这单花掉）。
  分三处各写一遍的必然结局是其中一条忘了退，而"忘退券"只出现在客诉里，不出于本机点两下就能复现的路径。
* D-123 **领券中心的 `claimed` 与 `myCouponId` 必须拆成两个字段**（本批自查出的真缺陷）：
  第一版把"我手上未使用的那张"当成了"我领过"，券一被核销，领券中心就把它显示回"可领取"，
  客户点下去撞到的是"每人限领一张"——表现像系统坏了。原则是**页面上按钮的语义必须与服务端拒绝的原因同源**。
* D-124 **订单出参只在 `discount_amount > 0` 时才回查券名**：绝大多数订单不用券，
  不能让列表每一行多跑一条 SQL；前端（下单页抵扣行、订单详情费用明细）只消费服务端下发的字段，不自己算折扣。
* D-125 **商家入驻"审核通过"这一步做三件事，缺一件就只是绿灯**（M-82）：
  ① `audit_status=2`，`pricing_service.get_demo_merchant()` 只认这个值，不通过就进不了承接池；
  ② 把申请人绑到该商家并转身份（`user_type=3` + 补 `merchant_admin` 角色），否则
     `scope.merchant_scope()` 返回 `None`，他一登录就是全量数据视野；
     补角色时只查 `(user_id, merchant_admin)` 而不查"有没有任何角色"——申请人本来就带 `customer` 角色，
     按后者判会跳过插入，表现为"审核通过但工作台是空的"；原有客户角色保留，下单身份与接单身份不互斥；
  ③ 站内信告知申请方。`get_demo_merchant()` 按 id 升序取，新通过的商家不会抢走演示承接方，这条有用例钉住。
* D-126 **驳回后重提复用原行**：同一张统一社会信用代码再提交时把原行改回审核中并清空
  `audit_opinion/audited_by/audited_at`，不新插一行——重提一次留一条历史，`uk_credit_code`
  还会把第二次提交撞成 500。另三条闸门：仅客户身份可申请、本人已有 0/1 状态时 409、
  `audit_status != 1` 不许重复审核（409 报出当前状态名），驳回必填原因。
* D-127 **PII 只在审核侧解密**：`_merchant_ser()` 按查看者身份决定明文还是脱敏，
  申请人看自己那条也是脱敏值——企业联系电话不是只有他一个人该看到的字段。
* D-128 **通知收件人按"这一动作的另一端"算，并按商家收窄**：客户动作（支付/取消）通知本商家
  `order:list` 持有者，商家动作（接单/拒单/完成）通知客户本人；收件人先过 `scope.merchant_scope`，
  否则 A 商家接单会提醒 B 商家，等于把别人的单量广播出去。
  "待支付"不发待接单通知——通知挂在支付成功之后，否则商家工作台会练出"看到通知也不用管"的坏习惯。
* D-129 **审批结果通知必须在 commit 之后**：`approve_plan/reject_plan/batch_approve` 先提交再逐单发，
  顺序反过来就会发出"已批准"而事务随后回滚。收件人取 `plan.dispatch_by`，为空才兜底
  `user_ids_with_perm("dispatch:plan", plan.merchant_id)`；客户侧另发一条并把方案号写进标题
  （批量审批时必须能对上是哪一单）。
* D-130 **告警类通知的三条规矩**：同一台设备重复标记只留一条（`notify.exists()` 去重）、
  解除时补一条恢复、**本来没被标记过就不许编造恢复告警**（用 `UPDATE ... .rowcount` 判是否真删掉）。
  收件人 = 平台侧 `monitor:device` + 本商家运维员，为此给 `scope.user_ids_with_perm()` 加了 `platform_only`。
* D-131 **通知写失败绝不拖垮主流程**：`notify()` 用 SAVEPOINT（`begin_nested`）隔离，异常只返回 `False`。
  用例把 `notify._INSERT` 指向一张不存在的表，断言支付仍然成功——"站内信写不进"不能变成"客户付款失败"。
* D-132 **新端点必须进 `PUBLIC`/`SELF` 白名单，这是被测试钉住的安全边界**：本批 4 个"只认登录"的端点
  （领券、券包、入驻申请、我的申请）第一次跑就被 `test_every_endpoint_is_classified` 拦下来，
  连同理由写进 `tests/test_perms_matrix.py` 的 `SELF`；`export_perm_matrix.py` 直接从那份名单渲染表格，
  所以"改了门禁没改文档"这种情况在机制上不可能发生。
* D-133 **清表名单补 `user_coupon`、`coupon`**：`coupon` 在 DDL 里没有种子行，用例自建的测试券不带走
  就会出现在下一条用例的领券中心里；`user_coupon` 是纯关系表，残留会让"每人限领一张"莫名变红。
  临时账号（`fresh_user`）持有的行也要先解绑 `users.merchant_id` 再删——FK 会在拆卸阶段炸掉，
  而那一串报错看起来像是被测代码出了问题。

经验教训：

* 本批没有一条难点在接口本身，全部在**口径**：券减多少、什么时候算减过、谁能收到通知、
  什么才叫"审核通过"。D-119/D-121/D-123/D-125 都是同一类——接口早就"能通"，但通的不是同一个定义。
* 唯一一个真缺陷（D-123 `claimed`）是自己读自己写的代码发现的，用户并没有报这个现象。
  它的形状很有代表性：**字段名比字段值诚实**，`claimed` 顾名思义是"领过没有"，
  一旦它被拿来兼放"还能不能用"，页面就会在正确的数据上给出错误的按钮。

  比让人记得写文档可靠得多（D-132）。

### B6-1 统计报表中心（契约 D8 / 设计06 M-12）

* D-134 **钱的口径只有一份表达式，报表中心与监管报告共用**：`NET_PAID = "o.paid = 1 AND o.status <> 8"`
  （`stats_service.py:54`）与 `PAY_EXPR/FEE_EXPR/DISCOUNT_EXPR`（:58-62）是常量，
  `/aux/report` 直接拼同一份（`aux.py:1047-1048`）。**退款不会把 `orders.paid` 改回 0**
  （它是流水 `direction=2` 那笔账），只判 `paid=1` 就把退掉的钱永久算进营收。
* D-135 **抽成写在订单上、不写在结算单上**：确认收货之前根本没有结算行，只读 `settlement`
  就永远统计不到"在途已支付"的抽成，商家收入虚高。费率用代码常量 `pricing_service.PLATFORM_RATE`
  ——与生成结算单时是同一份，所以"报表说抽成 X、结算单加起来也是 X"不需要对账。
* D-136 **区间是 `[start 00:00, end+1day)`，桶键不用 `DATE_FORMAT`**：`<= 23:59:59` 会漏掉带小数秒的边界记录
  （用例把"昨天一条 + 今天一条 = 两天窗口"钉死，`test_stats_report.py:236`）；
  `DATE_FORMAT` 的格式串带 `%`，而 SQLAlchemy 在 pyformat 驱动下对字面 `%` 的处理取决于版本，
  于是改用 `CAST(x AS DATE)` 与 `CONCAT(YEAR, LPAD(MONTH))`——**同样的桶键，没有那层不确定性**。
* D-137 **元数据跟着数据下发**：输出统一 `{meta, kpi, kpiLabels, kpiKinds, sections:[{columns,rows}]}`
  （`_result`，`stats_service.py:164`），列自带 kind（text/int/money/num）。页面卡片、图表轴、CSV 表头
  读同一份，杜绝"页面上叫实付金额、导出里叫 `pay_amount`"；前端也不再按字段名后缀猜哪一列是钱。
  空区间返回 **30 个全 0 的桶而不是空数组**（:153）——否则折线图上"没有数据"和"这三天没飞行"长得一样。
* D-138 **字段池就是后端白名单，请求参数只能选名字**：`DATASETS`（`stats_service.py:661`）一份结构同时
  渲染 `/reports/fields` 和校验 `_pick()`（:763），所以"页面选得出、后端说不认识"在机制上不可能；
  维度/指标/数据集三层不认识就 40000 并把可选值报回去。**SQL 表达式全部写死在本文件里**，
  用例专门拿"手机号密文列名"试注入（:317）。三个上限各有理由：366 天（日粒度再多是图上的一片糊）、
  自定义报表 500 组、空域穿行扫描 500 条计划（几何判定在 Python 侧）。
* D-139 **`report:view` 与 `report:export` 是两扇门**（p16，`report:export` id=47）：导出是"把整份经营数据
  落盘带走"，和看一页列表不是一个量级；权限被改窄时只关导出这扇门，不影响看数。
  商家管理员拿导出但**导不出别人的**——范围在 SQL 里靠 `scope.merchant_filter` 收，不靠权限点区分。

  M-11 驾驶舱的趋势线删掉前端写死的假数组，改读 `/stats/overview`（`DashboardView.vue:20`）。
* D-140 **契约 D8 的"Redis 结果缓存 5 分钟"这版明确不做，并把理由写进代码文档**：Redis 只在依赖清单里、
  运行链路一个键都没用（§5 非功能项），这里的聚合是几条走索引的 GROUP BY，演示规模单次 200ms 内；
  真要加缓存会在 `stats_service` 入口包一层 TTL，**不动下面的 SQL 口径**。写明偏差比假装做过便宜。

### B6-2 定时任务（需求 4.2.2-3 / 4.2.3 / DDL 分区 / 6.3.2）

* D-141 **任务函数是普通函数，APScheduler 只是它的一个调用方**：五个动作
  （`scheduler.py:96/126/175/224/273`）都能直接调用并返回"本轮干了什么"，调度层只管
  什么时候跑、跑崩了别带走线程（`_runner`，:326）。触发器在 `_job_defs()` 里现造而不是 import 时造——
  `IntervalTrigger` 把起算点定在构造那一刻，import 时构造会让首轮执行时间跟着模块导入时刻漂。
* D-142 **提醒去重按"业务事件"而不是按"用户"**：`notify.exists()` 的口径是
  `(user_id, biz_type, biz_id)`，拿它去重会退化成"每人各收一次"，而要问的是"这件事提醒过了没有"。
  事件级判定另起 `_notified(biz_type, biz_id)`（:82，靠 p17 补的 `idx_biz`）。
  这条口径顺带保住了更重要的性质：**这一轮没人可发，下一轮还得重试**——新商家还没配
  `order:list` 持有者时第一轮不发也不留痕，人配上就补上（用例 :169）。
  `message_notification` 从此有了三类新 `biz_type`：`reserve_remind` / `qual_expiring|qual_expired` /
  `coupon_offline`（资质那两个是分开的两件事，所以"即将到期"发过、真到期还能再发）。
* D-143 **资质状态为什么落库而券状态不落**（对 D-117 的边界修正）：`qualification.status` 的 2/3
  是**台账页要按它排序、筛选、出标签**的，"能被查询条件筛的状态"就必须是列；
  券包的 `4 已过期 / 5 券已停用` 只是展示推导，没人按它筛，所以继续读时算。
  推进方向单一：`UPDATE ... WHERE id=:i AND status IN (1, 2)`（:203-205）——
  **4 驳回是审核结论、3 是终态，绝不被日历覆盖**。预警窗口按主体分档（商家/人员/飞行器 7/15/15，
  `QUAL_WARN_CFG:41`），同一 `days_left` 下三种主体结论不同。
* D-144 **收件人按主体的形态算**：人员→本人；商家→`merchants.contact_user_id`；
  飞行器→商家内 `resource:qualification` 持有者，**已过期再追加平台侧同名权限持有者**
  （`_qual_recipients:154`）——飞行器的适航证掉了没人能替他续，必须有个能拦的人在场。
* D-145 **分区维护：预建默认开，DROP 默认关**（`track_partition_drop_enabled=0`）。
  预建没有副作用（存在即跳过），删真实轨迹数据必须有人显式点头。三条护栏：`pmax` 的月名解析
  返回 `None` 因而**永不进删除候选**（`_part_month:71`）、只有 `p\d{6}` 命名可删、表名过
  `_TABLE_RE` 白名单否则 `ValueError`。破坏性分支被做成**可测的**：`maintain_track_partitions(table=...)`
  接一张与 `flight_track` 同形的临时探针表，开关关时 `dueDrop=["p202501"] / dropped=[]`，
  打开后 `dropped=["p202501"]` 且 `pmax`、新预建分区都还在（用例 :271）。
  这个开关的 `value_type` 必须是 `number` 而不是 `boolean`：`/aux/configs` 的 PUT 只校验 `number`
  （`aux.py:656`），一个决定删数据的开关不能容忍 `int("true")` 失败后静默回落。
* D-146 **`FLASK_SIM_DISABLED` 读作"不要起任何后台线程"**（`scheduler.py:351`，与仿真器共用）：
  测试与探针脚本本来就带这个变量，复用同一个开关，比新增一个"忘了设就在背后改库"的隐患靠谱。
* D-147 **后台任务必须能回答"它到底在跑吗"**：`snapshot()`（:367）出
  `{running, disabled, jobs:[{id,name,trigger,nextRunAt}]}`，**没起来时照样把五个任务列全**——
  空表只会让人分不清"功能没做"和"开关关着"；`disabled` 与 `running` 分开，因为
  测试环境里的"没在跑"是预期不是故障。端点复用 `system:config`（`aux.py:668-677`，不新增权限点、不动迁移），
  前端把任务表就放在参数表下面（`SystemCenter.vue:43-72`），删数据的开关必须出现在点它的人眼前。
* D-148 **券下架只动模板、不动用户手上的券**：集合式 `UPDATE coupon SET status=2 WHERE ...` + `.rowcount`
  （不先查后写，也不用 `IN :ids` 展开绑定），`user_coupon` 一行不碰——券包的过期态本来就靠读时推导（D-117）。
* D-149 **`coalesce=True` + `misfire_grace_time=None`**：一轮迟了只补一次，夜里没开机就早上把当天的扫描补掉。
  资质状态与分区都是"越早对齐越好"的判定，宁可迟到不可跳过。

经验教训：

* **"字段有、参数有、页面有，但没有任何东西会自己跑"是一类独立的缺陷形态**，判据很便宜：
  全仓 grep 找不到那个字段的写入方。`qualification.status` 的 2/3、四个 `sys_config` 阈值、
  `flight_track` 的月分区，三个都中了这一条。
* **破坏性动作要设计成"默认不成立"**：DROP 的默认值是关、`pmax` 不可删、表名白名单、
  以及一个能注入同形表的参数。有了这个注入点，删除分支才第一次被真正跑过（而不是"注释说它会被跑"）。
* **线上验证是那台通宵的开发服务器顺手替我们跑出来的**：01:10 的 `qual_scan` 真的执行了一轮。
  关键是**别猜，去查 `updated_at`**——该列带 `ON UPDATE CURRENT_TIMESTAMP`，三行资质的它都没动，
  于是能断定 `UPDATE` 命中 0 行、种子本来就是 2/3，调度器在演示库上的唯一写入是那条 `qual_expiring` 站内信。
  同一条证据链也说明了反过来轻信"是调度器写的脏数据"会有多容易冤枉人。

实测结论：`pytest` **350 用例全绿**（B5 收尾 302，本批 +48：`test_stats_report` 35 / `test_scheduler` 13）；

## 十七、B6-3 契约端点收口：`POST /tracks/batch` 与设备心跳上报（2026-09-30 完成，367 例通过，演示库零写入）

* D-150 **契约缺口按"函数只有一份"来收，不按"再加一个端点"来收**：设计03 D6 把 `/tracks/batch` 写成
  "仿真器/未来真机统一上报入口"，而此前全仓唯一一段落帧代码在仿真器里、`source` 硬编码 1。
  收法是把"落帧 + 合规"抽进 `track_service.persist_frames`（`app/services/track_service.py:161`），
  仿真器（`flight_simulator.py:239`，`source=1`）与 HTTP 端点（`monitor.py:601`，`source=2`）调同一个函数。
  如果另写一份"上报专用"的落帧，契约那句"业务代码零改动"就永远是假的。
* D-151 **`source`/`violation` 这类"这条数据该不该信"的字段由服务端定死，请求体一律忽略**：
  上报方自填 1 就能把真机数据冒充仿真数据（或反过来），而 `source` 恰恰是判可信度的依据；
  地面站说自己没偏航也不算证据。合规判定因此仍然只有 `compliance_monitor` 一个出口，
  "打标必须在 INSERT 前"这条铁律（`compliance_monitor.py:281-290`）由共用函数继承下来，
  不会被第二个入口绕过。
* D-152 **批量上报的失败口径：逐帧丢、把原因带回去，整批都不可用才 400**（`track_service.py:97-144` +
  `monitor.py:597-600`）：上报是持续动作，一次抖动 200 帧里 3 帧越界，正确结果是 197 帧入库 +
  指名道姓的 `rejected`；整批 400 会让人开始怀疑整个链路。反过来"全批都是坏帧"还给 200，
  会让接入方以为链路通了、只是数据怪——所以那时候必须 400。
* D-153 **数值区间按列宽 + 物理意义写，顺手兜住 lng/lat 写反**（`_RANGE:45-50`）：
  中国境内经度 73~136、纬度 3~54 两个区间几乎不重叠，写反必然越界，而这是接入阶段最常见的手误；
  报错里那句"超出 73.0~136.0"当场就能让接入方自己发现。不做"看起来像坐标就接受"的宽容逻辑，
  越界写进 `DECIMAL` 只会被截断或 1264 整批回滚。
* D-154 **补报要有窗口，而且窗口挂在业务事实上**：`BACKFILL_WINDOW_SEC=900`（`monitor.py:551`）——
  `status=3` 执行中随时可报，`status=4` 只接受落地 15 分钟内，理由是链路最后一段断了的那截航迹
  还在 GCS 本地排队。未来的帧（机载时钟快了）与 7 天前的帧都不收：前者会污染"最后一次听到它"的
  心跳判定，后者已经没有回放价值。
* D-155 **上报不推状态机（D3 铁律再确认一次），心跳也不解除人工失联标记**：`apply_telemetry:218-242`
  只写 `plan.current_*` / `last_report_at` / `aircraft.online` 与位置电量，`plan.status`、`aircraft.status`
  一律不碰；人工标记只能人工解除，否则运维标的"图传丢了但遥测还在报"会被下一跳心跳冲掉，标记就成了摆设。
  回执用 `lostMarked` 把这件事说白："心跳收到了，但状态还是失联"。
* D-156 **心跳必须显式写 `updated_at`**（`monitor.py:657`）：MySQL 的 `ON UPDATE CURRENT_TIMESTAMP`
  只在"值真的变了"时刷新，于是一次"电量和位置都没变"的心跳会 0 行改动、设备永远显示离线。
  这与 §19 拿 `updated_at` 当取证是同一枚硬币的两面：正因为它不无脑刷新，它才能同时当"心跳时钟"
  和"改动证据"——所以要显式赋值，也才敢用它来自证。同理 `last_report_at` 记服务器时间而不是帧时间。
* D-157 **同一份状态推导只允许长在一个地方**：`_aircraft_state`（`monitor.py:417`）与 `_station_state`（`:429`）
  从 `devices()` 里抽出来，给 GET 与心跳回执共用。不抽的话心跳想带上状态就得把"在飞且心跳断了才算失联"
  再抄一遍，两份"看着一样"的推导迟早分叉。
* D-158 **命名沿用"上报的是证据不是结论"**：新端点叫 `devices/heartbeat`，不叫契约里压根没写过的
  `devices/online`。设备自报"我在线"不是证据，它报的是"我还在说话 + 我看到的这几个数"，
  在线与否仍旧由推导给出。契约的 `GET /devices/online` 对应读侧 `GET /api/monitor/devices`（B3 已交付），
  本批补的是那张推导表的**写侧**。
* D-159 **同名歧义在接口层拆，DB 列与既有契约都不动**：接口层 `deviceType`（1 机载 / 2 地面）改名
  `terminalType`（`monitor.py:347-351` 留注释说明），`device_lost_mark.device_type` 列名不动、
  `auth.py:13-15` 的 `Device-Type: PC|Mobile` 头不动（那是契约全局约定），
  `tests/conftest.py:276` 与 `test_smoke.py` 里登录体的 `deviceType` 也保持原样——它俩本来就不是一件事。
  判据是改名的爆炸半径：接口层只有 `Devices.vue` 一个消费者（6 处），而留着它，真机接入文档里
  两个 `deviceType` 同时出现时一定会被问住。这是一次破坏性改名，仍做，理由写在 §20.4。
* D-160 **`dedupe` 只对外的上报入口开**（`persist_frames(..., dedupe=True/False)`）：重传是网络侧的常态，
  `_known_times:150` 拿这批帧的时间区间做一次 `BETWEEN` 查询；仿真器的帧是连续推进出来的，
  每 tick 多查一次库纯属白花。共用一个函数不等于共用一组默认值。
* D-161 **场站的心跳时钟单独一列，不与 `updated_at` 合用**（`vertiport.last_heartbeat_at`，迁移 p18）：
  地面设备的状态以前只看 `status`（开放即在线），这在"没有链路"的前提下自洽；D-158 的心跳端点
  接受 `terminalType=2` 之后，同一列 `updated_at` 同时承担"资料变更时间"和"最后一次心跳"，
  于是**从没报过的**与**报过之后静默的**两种场站在库里长得一样。实测现场就是演示库那三台：
  最后一次写入 9-23、阈值 60 秒，页面显示「在线」而页头写着「心跳阈值 60 秒」。
  判定改成三档（`_station_state:429-439`）：有心跳按心跳、没心跳回落到运营状态、人工失联仍然压过推导；
  `heartbeatKind` 同步由这一列决定，页面「· 资料更新」那个后缀从此才说的是真话。
  列**可空且不回填**：存量行全 NULL 意味着行为与加列前完全一致，不会让演示库的设备一夜之间集体掉线。
  机载侧不补这一列，因为 `aircraft.online` 本身就是设备报上来的标志，"在线"必然蕴含一次真实上报，
  混列最多让时间列少一个后缀，判不反状态——这一点写进 §20.6，免得下次有人顺手把两边改成两样。

经验教训：

* **"文档里写了统一入口"与"代码里只有一个入口"是两件事**，判据和 §19 一样便宜：
  `source=2` 这一路在全仓找不到写入方。B6-2 的病是"字段没人写"，B6-3 的病是"入口只有文档"，
  同一类缺陷的两种表现——都该在验收清单里问一句"谁写这一列"。
* **把"两路数据同表共存"当成收尾断言**：`test_simulator_and_gcs_frames_coexist_in_one_table`
  直接断言一张表里 `{1,2}` 两种 `source` 并列，这才是"统一入口"的可执行定义。
  只测"端点能写进去"的话，将来把代码改回两段照样全绿。
* **造"偏航"点必须绕开禁飞区，否则测的是另一条判定**：航线本身是折返的

## 十八、现象级反馈：三层权限名单对不上，运维点人员管理吃 403（2026-09-30，**修法已被 §十九 替换**）

用户报的是现象："登录运维账号成功，点人员管理提示没有操作权限：resource:qualification 或 system:user"。

## 十九、用户推翻 §十八 的修法：查看是需求，不能拿隐藏当答案（2026-09-30 完成，本轮读门放宽 + 自助口 + 站内信寻路）

但是这并不只是运维的问题，别的人也要看到排班的情况啊，所以我们就只给查看的页面，那些没权限的。」
前半句确认了 §十八 的诊断（要看、没权、所以报错），后半句改的是结论：**"要看"是业务事实，
把它隐藏起来只是把 403 换成空白**；而且这个诉求不属于运维一个角色，所有排班相关的岗都一样。

* D-163 **冲突时先问"这是读还是写"，读门可以按页面准入名单放宽，写门一寸不动**（取代 D-162）：
  `resource.py:338-339` 的 `@perm_any_required` 加上 `resource:schedule`、`resource:aircraft`，
  让资质台账的放行名单成为人员管理页准入名单（`menu.ts:60-61`、`router/index.ts:226`）的**超集**；
  `POST /qualifications/<id>/audit`（`:307`）继续只认 `resource:qualification`。
  D-162 里"不许为了让报错消失而改授权边界"这条判断依然成立，本轮也确实**没有给任何角色补权限点、
  没有新增权限点**——`permission` 与 `role_permission` 种子一行未改，改的只是"读"承认哪些已有的 code。
  区别写在重新生成的 `docs/接口权限映射表.md` 里：`GET /resource/qualifications` 授权到 **5 个角色**，
  `POST .../audit` 授权到 **2 个角色**。只读扩大、写不变，这才是"只给查看的页面"。
* D-164 **自助口用身份门而不是权限点**（`GET /api/resource/my-duty`，`resource.py:404-406`）：
  第二个提问是"那些排班不同的人员怎么收到消息——看着只有运维有界面"。链路本来通着
  （`scheduler.py:154-172` 对 `subject_type=2` 把预警直接发给本人 `sid`），缺的是**落点**。
  修法不是给机长补 `resource:schedule`（那等于让机长能改班表），而是 `@staff_required`
  （`user_type` 3~6，`auth_kind="staff"`，`req_perms=()`）+ 视图里写死 `subject_id/user_id = 本人`。
  这类端点进 `test_perms_matrix.py` 的 `SELF` 名单（`:62`），"每个端点必须被分类"那道门照样过得去。
* D-165 **不带权限点的端点，输出面按"最小可回答"裁**：`dutyBoard` 只出
  `{shiftType, shiftName, count}`，不出姓名。机长问的是"今天几个人在值班"，
  不是全区花名册；一个谁登录谁能读的口子如果返回名字列表，就是给所有运营岗开了 personnel 的旁路。
  判据做成断言而不是共识——`test_duty_board_gives_counts_not_names` 校验 key 集合，多一个字段即红。
* D-166 **通知落点按权限寻路，进不去就明说"仅通知"**（`constants/msgRoute.ts` + `AdminLayout.vue:167`）：
  每条 `biz_type` 的候选落点带 `anyOf`，解析器按顺序取第一个进得去的（资质类：有 `resource:qualification`
  去台账，否则退到 `/admin/profile`，任何运营岗都进得来）。落点名直接显示在消息行里。
  这条比"跳转失败再兜底"更硬的原因是**动态路由只按权限注册**：推一条没注册的路径会被守卫送回首页，
  用户看到的现象就是"点了没反应"，比报错更难查。
* D-167 **页面准入与接口门的一致性交给测试，不在前端再写一份 `v-if`**：删掉上一版的 `canQual`。
  在路由门已经要求 qualification|schedule 任一的前提下，`canQual` 恒真，是一条永远不会为假的分支；
  真正会退化的是后端那道门，所以不变式落到 `tests/test_qual_ledger_view.py:105`（只有 schedule 的角色读得到台账），
  并在 `Personnel.vue:157-162` 的注释里写明"读与审是两件事、后端必须放行这份名单的超集"。
  `canAudit`（`:163`）保留，它管的是"复审"这一个动作，与页面可见性无关。

经验教训：

* **报错有三种正确反应，只有一种是错的**：补权限点（动授权边界，错）、隐藏数据（把 403 换成空白，需求没满足）、
  放宽读门并保住写门（对）。判据不是"哪个改动最小"，而是"用户的真实动作是什么"——运维要排班，排班要看着证。
* **`todayOnDuty` 这种"看起来能省一次查询"的字段要单独算**：它跟 `from/to` 查询范围语义不同
  （查下个月班表时"我今天上不上班"仍要回答），合并成一个查询就会随范围漂。
* **Mock 残留在自检时会自己冒出来**：重写 `Profile.vue` 时发现改密码那句是"已保存（Mock）"，
  换成真调 `changePasswordApi`（`:125`）。这类只在"页面被真读一遍"时才暴露，属于 §7"看着有其实没通电"那一类。
* **迁移铺的滚动班表算测试基线的一部分**：`staff_schedule` 的 `uk_user_date_shift` 会被
  `20260929_p10_schedule_shifts.sql` 按 `CURDATE()` 铺未来 7 天，测试插"今天的班"必撞 1062。
  `ledger.shift()` 的处置是撞了就返回既有行、**并且不登记回收**——那张班不是本次用例创建的，删它等于动别人的基线；
  标记行改放 `+20 ~ +26 天`这段没被铺到的窗口。同类前提：`conftest._truncate()` 不清
  `qualification`/`staff_schedule`/`users`/`permission`，写这四张表必须自己快照回收。

### D-168 查看与修改拆成两个权限点，而不是给角色加"半个"权限

### D-169 入口态用列默认值钉，而不是"新建时记得传 status=0"

`qualification.status` 的 DEFAULT 是 1（插入即有效）。开写入口之前先把默认改成 0，并且**三个地方同步**：

另外确认 `scheduler.scan_qualifications()` 只推进 `status IN (1,2)`，新落的 0 不会被时间扫描顺手改掉——
否则"待审核"会被定时任务替人放行。

### D-170 附件存 `static` 外面，键形状由服务端生成并在读时二次校验

`UPLOAD_ROOT = instance/uploads`（`config.py:51`，`MAX_CONTENT_LENGTH = 10MB` 同处 `:54`）。
键 `qualification/YYYYMM/<uuid32>.<ext>`（`resource.py:466-482`），读的时候按同一条正则
（`QUAL_FILE_KEY_RE` `:420`）再验一次形状——库里被塞进 `../../etc/passwd` 也送不出去，这条由测试钉住。

白名单里没有 html/svg，再加一层挡浏览器自己猜类型。

### D-171 大小上限按"全站请求体 10MB"实现，而不是需求书的"单文件 50MB"

需求书 6.3.1 写 50MB。放开 50MB 是给**整站请求体**开一个 5 倍的口子（Flask 的 `MAX_CONTENT_LENGTH` 是全站量），
而批量下单 CSV 上限 200 行、轨迹单批 2000 帧都远在这条线以下。超限在 `_handle_http_error` 特判 413，
回中文可读消息（`errors.py:30-33`）——这条原先会掉进通用映射，现象是一句英文 "Request Entity Too Large"。

**取舍记录**：断点续传不做（要 upload session 表 + 临时片目录，超出这一层必要）；覆盖式"换附件"不做
（会抹掉复审留痕，改件走"驳回 → 重递"）。需求书那一行因此改判 🟡，没有假装满足。

### D-172 两条写口共用一个落库函数；原件读口拆两条

| 口 | 门 | 主体 |
| --- | --- | --- |
| `POST /qualifications`（`resource.py:558`） | `resource:qualification` | 表单给，商家侧被 `scope.merchant_scope` 锁死 |
| `POST /qualifications/mine`（`:577`） | `@staff_required` | 写死 `(2, 本人)` |
| `GET /qualifications/<id>/file`（`:592`） | `QUAL_READ_PERMS` 任一 + 商家归属 | 与台账读同一份名单 |
| `GET /qualifications/mine/<id>/file`（`:632`） | `@staff_required` | 主体条件写在 **WHERE** |

四个入口都收敛到 `_create_qualification()`（`:497`）/`_send_qual_file()`（`:619`），所以不存在"谁建谁有效"。
第四条口是本轮现场发现的缺口：台账那道门认四个权限点，机长一个都没有，**装饰器先拦，视图里的"本人"分支
根本轮不到执行**——"我上传的证我自己看不到"。自助读必须另开一条，越界读到的是 404（不给试探者确认 id 存在）。

否则台账第一天就会出现"某个机长名下一本营业执照"这种没法复审的行。

### D-173 原件不走 `request` 实例，也不给静态直链

`utils/download.ts:83-115` 新增 `viewStoredFile()`：裸 axios + `responseType: 'blob'`。
两个理由都是硬的：响应拦截器只认 `{code,message,data}` 信封，Blob 进来会被当成"解析失败"弹错；
而接口只认 `Authorization` 头，`<img>`/`<a>` 发不出这个头，把 token 拼进 query 又等于写进地址栏和历史记录。
`window.open` 在 await 之后已不在用户手势里，可能被拦截，所以拦下就退化成下载并说明原因。

## 二十二、把"跑通"换成能重跑的断言（2026-10-01 完成，后端 483 例通过、演示库一条三列写回）

**D-179 端到端链测只断言"下一环读到的值等于上一环写进去的值"**
`tests/test_flow_e2e.py` 与既有两份测试的分工是清楚的：`test_state_machine.py` 管状态机能不能这么走，
`test_perms_matrix.py` 管每个端点有没有门禁，两者都不管**跨模块的接缝**——券抵扣算进订单没有、

## 二十三、一键入口也是被测对象：路径靠探测、等待靠端口、杀进程靠归属（2026-10-01 完成，两个 .bat 重写）

产品测到 483 例之后回头看了一眼用户每天点的那两个 `.bat`，发现一个已经半年没工作过、另一个每天都在
准备砸掉别人的东西。**入口坏了不会有人报修**，因为它坏的时候只是"打不开"。

**D-185 启动脚本按标记文件定位代码目录，不写死相对路径**
`一键启动.bat` 写于 9-23，代码在 9-28 整目录搬进 `代码/`，它还 `cd /d %~dp0backend`。
`start "…" /min cmd /c "cd /d <不存在的目录> && python run.py"` 的行为是：子窗口报一句
"系统找不到指定的路径"、`&&` 短路、什么也不起，而父脚本按既定剧本打印 `Done! Opening browser`
并 `exit 0`。这类失败最难发现，因为它把"我启动了"这件事演完了。现在用
`for /d %%D in ("%~dp0*") do if exist "%%D\backend\run.py"` 找目录：判据是标记文件而不是名字，
目录再搬、再改名都不影响；找不到就明确说"把两个 .bat 放回项目根"并 `exit /b 1`。
顺带一条：**脚本正文保持纯 ASCII**，路径里的中文来自 `%~dp0` 运行时展开，
这样不必在 GBK 控制台的 .bat 里塞 UTF-8 字节，也不必 `chcp`。

**D-186 就绪判断用端口轮询，不用固定 sleep**
原来是 `timeout /t 4` 起后端、`timeout /t 8` 起前端，然后无条件开浏览器。慢一点的机器会把浏览器开在空端口上，
快一点白等十几秒，而且失败时用户只知道"打不开"。现在 `:serve` 先看端口是否已 LISTENING（是就跳过，
不再起第二份抢同一端口），否则起进程后按秒轮询 `netstat -aon`，后端 60 秒、前端 90 秒为上限，
超时就报"port X 没起来 + 去看那个最小化窗口 + 常见原因是 MySQL 或 .env"。
预检按"缺了必然起不来"划线：venv 里的 `python.exe`、`node_modules\vite\bin\vite.js`、`npm` 在 PATH
这三项缺了就中止并打出补齐命令；`.env` 与 3306 有无监听只警告，因为那两件事各有合法替代。
浏览器放在两个端口都验证之后才开，末尾再打一次 `/api/health` 只取 `status` 行——这是给用户看的第一句实话。
循环里的等待一律用 `ping -n N 127.0.0.1`：**`timeout` 在 stdin 被重定向时会直接报错退出**，
本轮从管道里跑脚本时踩到了，用 `timeout` 的启动器没法被自动化验证。

**D-187 关闭脚本按归属杀，绝不按镜像名杀，且拒绝不认识的 PID**
原脚本两行 `taskkill /IM python.exe /F` 与 `/IM node.exe /F`：把整机 Python 与 Node 一起端掉。
射程里会有正在跑的 pytest、别的项目的 dev server（本轮快照里就有一条 `D:\web\vue` 的 `npm run dev`）、
编辑器的语言服务。现在三段：① 自家窗口标题 `tianshu-backend*` / `tianshu-frontend*` 连树杀；
② 仍占着 5000/5173 的按端口属主 PID 杀（覆盖从终端手起的那类）；③ 等 2 秒补一次，再逐端口报告
`released` 或 `still busy` 并贴出占用行。交 PID 给 `taskkill` 前先 `tasklist` 校验镜像名是
`python.exe`/`node.exe`，不是就打 `left alone`——别人的程序占了这两个端口也不该死在启动脚本手里。
只按 PID + `/T` 就够，不必反查父进程：Werkzeug 只在子进程以退出码 3 结束时才重生
（`.venv/Lib/site-packages/werkzeug/_reloader.py:266-277`），`taskkill` 给的是 1，父进程拿到非 3 直接 return，
`npm` 与 `cmd /c vite` 两层壳也在孩子死后自退。实测杀完 `python/node/cmd` 进程数归零、两端口释放。
另记一条工具层的坑：从 Git Bash 调 `.bat` 时 **`>nul` 会被 MSYS 改写**，脚本表现为
"系统找不到指定的路径"+exit 1，重定向到真实文件名则正常——双击不会有这个问题，别把它当成脚本缺陷去改脚本。

**D-188 演示口令可以继续打在启动脚本里，`.env` 里的值不行**
启动脚本原本就打印 `Password: Admin@123`，那是 `frontend/README.md` 演示账号表里的公开种子口令，
留着是给答辩用的；`.env` 里的 DB 密码、JWT/AES/HMAC 密钥一律不进脚本、不进输出。

实测证据（冷启动 5 秒两个端口都 up、health `UP`、vite 200；重复运行走"already listening"分支不起第二份；
带窗口标题与不带窗口标题两类进程都被收干净，交给 `taskkill` 的 PID 只有端口属主那两个）见《差距分析》§二十六。

### 二十一、交付前全量点验（2026-10-08）

**D-189 读口的"行级范围"是独立一层，权限点与 SELF 名单都不代表它**
本轮两个越权缺陷（订单读口把 69 单摊给空管/运维/机长；轨迹回放让 B 商家回放 A 商家航线）
都不是"忘了挂装饰器"：装饰器在、矩阵用例绿、菜单也没有那一项。真正的洞是——
`SELF`（仅登录态）与"权限点命中即放行"这两类端点**没有任何用例校验可见行**，
`test_perms_matrix.py` 只管"这个身份能不能进门"，进门之后拿到的是全量表。
所以定下口径：**凡读口的返回内容里带别人的人/货/位置，就必须有一道视图级门**，
并且同一份"谁能碰这条记录"的口径要在读写两边同时落实（写门 `_reportable_plan` 早有了，读门这次补齐）。
落点：`app/blueprints/orders.py:36-48`（`_reader()`：客户按登录态、员工侧另需 `order:list`）、
`app/blueprints/monitor.py:182-195`（`_visible_plan_query()`：平台全量／本商家／本人执飞）。
回归：`tests/test_order_query.py:212`、`tests/test_monitor_replay.py:106`；
并在 `test_perms_matrix.py:426` 注明"门在此用例、行级在 row_scoped 用例"。
判据仍然看 `docs/接口权限映射表.md`：本轮没动任何权限点的授予名单，前端也只做收窄不做扩权。

**D-190 门户与管控台的读门按"身份"分层，不能只用权限点或只用登录态**
`@perm_required("order:list")` 直接套到门户订单口会把客户整片 403（客户角色权限点为空），
只挂 `@jwt_required()` 又会把台账摊给平台岗位——两头都不对。定式：
`user_type in (1,2)`（客户/收件侧）按登录态放行，其余身份必须有对应权限点，
写在视图层而不是 service 层，因为它服务的是"这个身份该不该看见这一页"，不是"这条记录归谁"。
员工身份点进 `/portal/*` 现在是 403＋提示，不再泄漏数据；是否要在路由层彻底禁止员工进门户，
留给产品拍板（测试记录 §7.1 问题 ③）。**——2026-10-08 第二轮已拍板并落地：路由层不挂，见 D-193。**

### 二十二、第二轮：三个待拍板口径同日落地（2026-10-08，测试记录 §9、差距分析 §二十八）

**D-191 大屏这类"态势读口"要分两层判：能不能看（脱敏）＋ 看哪些行（范围）**
`/api/monitor/screen` 原来只有第一层：`user_type in (3,4,5,6)` 就不脱敏，其余一律脱敏，行级永远是全表。
单层判定留下的洞是"商家调度员在自家屏上看得见隔壁商家的机队位置、今日单量、违规条数"——
身份打码打不掉经营数据。定式：脱敏分支管身份（机长姓名／收货门牌／货物品名），行级范围单独一层，
且判据必须与同一条数据的其它读口同源（这里复用回放的 `_visible_plan_query`，`monitor.py:96-114`）。
匿名与客户**不裁行**：投屏口径本来就是"态势公开＋身份脱敏"，给他们裁行会把脱敏分支变成空屏，
那是造新问题不是修问题。统计口径同理要跟着行门走——违规计数为这个从 raw SQL 改成了 ORM。

**D-192 演示库的"资源不够"要用幂等迁移补，不要靠人手点、也不要改服务端规则**
5 张待调度订单被"起飞场没有停放的飞行器"挡死，最省事的两种做法都不采纳：
现场点 UI 造资源（不可复现，换库又没了），或放宽 `_validate_resources` 的"飞机必须在起飞场"（那是
真业务约束，放宽等于把 2026-10-08 刚修好的推荐口径再拆掉）。补的是数据不是规则：
`sql/migrations/20261008_p23_park_aircraft_vp004.sql` 给温州商学院示范区停两架闲置满电机，
按 `station_no` 而不是 `id` 定位场站（id 是演示库自增出来的，换库就飘），`INSERT IGNORE` 靠
`uk_aircraft_no` 幂等。该场站是「场站管理」按真实地理编码点出来的、只存在于演示库，
所以在只有 DDL 种子的库里这条迁移选不到行——这是预期的空操作，不是漏配，写在迁移头注释里。

**D-193 门户路由按身份挂，不是按权限点挂，也不是"进去再拦"**
`/portal` 整棵子树从 `constantRoutes` 挪进 `buildDynamicRoutes`，只有客户（`userStore.isCustomer`，
`user_type 1/2`）才注册。三层判据各管一件事，别再混：门户是**身份**门（客户 vs 员工），
管控台页面是**权限点**门，接口返回哪些行是**数据范围**门（D-189/D-191）。
员工路由表里没有 `/portal/*` ⇒ 落 404 兜底 ⇒ 守卫送回自己首页，门户组件不被实例化，
`onMounted` 里那些客户端接口一次都不发——所以顺带消灭了页内 403 与那条未捕获 rejection 的 `[Vue warn]`。
选"不挂"而不是"挂了再拦"，是因为前者压根不产生"我能点进去但报错"这种困惑；
代价是这条判定不看后端菜单（menus 里没有门户项），所以身份是唯一依据，这点在 `stores/user.ts:21` 注释里写死了。

### 二十三、第三轮：场站机位占用数与设备在线列表的行门（2026-10-08，测试记录 §10、差距分析 §二十九）

**D-194 「当前占用数」按停放飞行器派生，不读 `vertiport.occupied_count` 那一列**
观察项⑦：调度台／场站台账／设备在线三处都在显示"温州商学院示范区（0/4）"，而那台站实际停了两架机。
根因是这一列**从建库起就没有写入方**——场站心跳上报的是桩位 `charger_available`（`monitor.py:759-761`），
机位从来不上报，DDL 种子里它永远是 0。两个可选方向里不选"由心跳/预约写入"：心跳上报是外部设备的话，
仿真链路里没有机位这路数据，硬造等于给自己编一个来源；预约写进这列会把"预占"和"实占"混成一个数字，
进度条没人能解释，而且预约是按时间窗算的，一个数无法表达。
定的是**读侧派生**：`dispatch_service.station_occupancy()`（`app/services/dispatch_service.py:117-134`）
按 `aircraft.current_vertiport_id` 分组数停放，三个读口（`resource.py:75-82`、
`dispatch_service.py:146-166`、`monitor.py:558-572`）都调它，出参键名 `occupiedCount` 一字未改，前端零改动。
派生里有个坑必须写进注释：起飞只把 `aircraft.status` 置 2、**不改** `current_vertiport_id`，
降落才由 `_do_land` 迁到终点场，所以在飞的机器数据上还挂在出发场——判据是 `status<>2`，
与 `idle_aircraft()`／`_aircraft_busy_ids()` 同一份"什么叫做完这一趟"的时间窗。
充换电(3)／维保中(4)／故障离线(5) 都算占用机位，它们确实停在那儿。
列本身留在库里（MySQL 8 没有 `DROP COLUMN IF EXISTS`，删它就无法配幂等迁移，违反"改库必须幂等"），
只在 `models/resource.py:22-24` 标注"没有写入方，读侧走 station_occupancy()"，别再读它。
占用数是**场站级基础设施口径**，商家侧也看到全量：它不指明是谁的机，且场站预约冲突提示本来就把
"该时段机位已被占满（1/1）"告知申请人（`resource.py:892-904`），这里收窄成"你家的机"反而和那套口径打架。

**D-195 设备在线列表补行门：`monitor:device` 给了商家侧运维，就必须按行裁**
派生口径要把三个读口对齐时顺手复查了 `/api/monitor/devices`，发现它和上一轮的订单读口、回放读口是同一族问题：

而 SQL 里没有任何商家条件（原 `monitor.py:519-527`），商家运维打开这一页能拿到别家机号、实时经纬度、
在飞任务号——D-189 说的"门关了、行没裁"在这儿第三次成立。
先写用例看它红：`tests/test_monitor_devices_scope.py` 首轮 2 条失败（`{1,2} != {2}`），确认泄漏不是推测。
修法是收窄：飞行器按 `merchant_id = 本商家`，场站按"本商家 + 公共场站（`merchant_id IS NULL`）"，
判据取自 `scope.merchant_scope()`，与 `list_aircraft()`、调度台 `list_resources()` 同源；
平台侧 `mid is None` 不拼条件，全量口径不动（`monitor.py:521-552`）。
这是**收窄不是扩权**：商家侧少看别家的行，平台侧一行没变，权限点授予名单与 `docs/接口权限映射表.md` 一字未动。
