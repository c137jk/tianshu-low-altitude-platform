D. 全局接口约定（两个人都必须遵守）
1. 统一响应体 {code, message, data}，异常不暴露堆栈与数据库信息；分页统一 pageNum/pageSize。
2. 请求头 Device-Type: PC|Mobile：业务逻辑只写一份，在 schema 层做字段裁剪（如 OrderPcSchema / OrderMobileSchema），代码复用率 ≥80%。
3. JWT 走 Authorization: Bearer；PC 有效期 8h、移动端 2h，支持 /auth/refresh 无感刷新；手机号/邮箱/身份证出参强制脱敏。
4. 状态机唯一入口在 D3 的 service 层：任何端只能调动作接口（approve/takeoff…），禁止直接 UPDATE 状态字段。
5. 操作日志由装饰器/中间件自动写 operation_log，不靠各接口手写。
6. 所有外部系统只允许经 Mock 适配层访问（payment/weather/utm/gcs 四个 adapter），将来接真系统只换 adapter，业务代码不动。
7. 坐标一律 GCJ-02（高德坐标系），仿真器造点、库内存点、前端绘点三端统一，禁止混入 WGS-84。
E. 两人分工与接口交付顺序
同学甲 · 前端为主
PC：框架布局 → D1 登录 → D2 下单/列表 → D3 调度页 → D5 空域地图（高德图层）→ D6 监控大屏 → D4/D8/D7/D9 页面；后期合啃 UniApp 四角色路径。
同学乙 · 后端为主
Flask 骨架+MySQL 建库 → D1 → D2 → D3 → D5 → D6（含仿真器/WS）打通闭环 → D4 并行 → D7/D8/D9；Swagger 先行，给甲 Mock 响应示例。
接口交付顺序（闭环优先）：D1 认证 → D2 订单 → D3 调度/任务 → D5 空域校验 → D6 轨迹/WS，这五个跑通即等于「申请-审批-调度-监控-结算」主干贯通；D4 资源并行补；D7/D8/D9 最后迭代。第 1–2 周乙必须先出 P0 接口的 Swagger 骨架与假响应，甲不等后端即可开工。

F.3 双凭证与无感刷新（补齐 D-03 / 全局约定第 3 条）
后端：login() 一次返回 token（PC 8h / 移动 2h）+ refreshToken（REFRESH_TOKEN_DAYS=7），两者都带 user_type / roles / device 三个 claim，续期时靠 device 还原有效期。 POST /api/auth/refresh 用 jwt_required(refresh=True) 只认刷新凭证，并现查账号状态——冻结/注销的账号返回 40300「无法续期」；续期是唯一的重发卡时机，这道闸不放就等于冻结形同虚设。
前端：utils/request.ts 命中 401/40100 时先静默续一张、重放原请求，续不动才清登录态跳登录页。三条硬规矩：① 登录/续期/注册自身不触发续期（否则 401 递归）；② 同一时刻只允许一条续期请求在飞（大屏 2.5s 一拉 + 页面并发，不设门闩就是并发打后端）；③ 两张票一起存 ts_token / ts_refresh_token、一起清，只清 access 会被残留的刷新票悄悄续回来。
边界：本期无 Redis，所以刷新凭证不能吊销——退出登录只是前端丢弃凭证，7 天内泄露的 refreshToken 仍可用。这条与"登录失败锁定""token 黑名单"一起留给接 Redis 的批次，属已知欠账（设计07 第八节同步记录）。
